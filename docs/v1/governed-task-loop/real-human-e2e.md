# Real human-level generated-feature acceptance harness

Tracking: [#58](https://github.com/anthonykewl20/kogg/issues/58), research
phase [#61](https://github.com/anthonykewl20/kogg/issues/61), pseudocode phase
[#62](https://github.com/anthonykewl20/kogg/issues/62).

## Status

Research and production pseudocode are complete as of 2026-08-26. This packet
contains no production code. Production remains gated by the ordered prototype
and implementation issues and by Foundation
[#47](https://github.com/anthonykewl20/kogg/issues/47).

The research recommendation is a Playwright-driven, product-black-box acceptance
harness with two production launch adapters: authenticated browser and native
Electron. A scenario starts from a clean profile and disposable real Git
repository, drives only controls a person can see and use, crosses real owned
filesystem/process/provider/Ranex/Linux boundaries, and then verifies both the
visible result and independently observable external effects. The harness owns
only setup, orchestration, observation, artifacts, and teardown. Product services
remain owned by Kogg, Theia, providers, and Ranex.

“Human-level” does not mean imitating mouse coordinates. It means the action that
causes product behavior is discoverable and visible in the production UI; the
harness selects it through an accessibility role, label, command palette, menu,
or rendered control. Direct RPC/service calls, database writes, pre-generated
patches, internal command execution, and mocked owned boundaries cannot substitute
for the user action or product outcome.

## Scope and acceptance invariants

The V1 harness must prove that a feature generated by the governed task loop can
be accepted as a user would experience it:

- a real task begins from a frozen specification and one registered real Git
  repository/worktree;
- real agents/providers and Ranex produce, execute, evaluate, and bind the change;
- the generated code is built into the production browser/Electron application
  or an approved signed extension boundary, not injected into a test-only shell;
- Playwright opens the production entrypoint with a clean profile and uses visible
  controls to exercise the generated behavior;
- real Git, filesystem, subprocess, qualified Linux confinement, diagnostics,
  source maps, and lifecycle evidence agree with the UI result;
- success and the principal refusal/failure/timeout/cancel/restart paths are
  exercised; and
- every product and harness process is joined, killed by its proper owner, drained,
  and proved absent before the temporary state is removed.

The harness may create disposable repositories, local deterministic provider or
registry fixtures, credentials containing random non-production values, input
files, OS calibration processes, and clean application profiles. It may inspect
Git/filesystem/process state after the visible action. These are setup and oracle
boundaries, not shortcuts through product services.

## Source findings

### Playwright 1.62.1

Locators resolve against current DOM state and actionability waits check visible,
stable, receiving-events, and enabled conditions before an action. Role/label/text
locators therefore represent a stronger human contract than CSS coordinates or
DOM implementation traversal. Exact app-owned `data-*` locators are acceptable
only where a rendered repeated structure has no meaningful ARIA relation; they
must not invoke hidden behavior.

Browser contexts isolate cookies and storage. Kogg additionally needs an isolated
backend state directory and Theia/Electron config profile because browser context
isolation alone does not isolate filesystem, credentials, SQLite, workspaces,
terminals, or plugin hosts.

Playwright traces, videos, screenshots, console logs, and network data can contain
prompts, source, paths, cookies, authorization, provider bodies, and personal data.
They are not automatically safe support artifacts. Kogg must use deterministic
disposable content, redact structured logs, suppress/avoid sensitive network-body
capture, scan artifacts, and retain only the minimum failing evidence.

The Electron API launches a real process and returns its windows, main-process
evaluation boundary, and process handle. Main-process evaluation is acceptable
only for harness launch metadata, window enumeration, menu activation when a
visible shortcut cannot be delivered, and cleanup observation. It cannot execute
Kogg feature commands, mutate product services, or assert success on internal
state.

### Electron 42.3.0

Electron has distinct app ready, window ready-to-show, renderer load, app quit,
and child/backend lifecycle boundaries. A first window can exist before Theia
plugins, SCM, tasks, or commands are ready. The harness must wait for the rendered
workbench and retry a visible discovery action where asynchronous plugin command
registration is the behavior a person would also wait for.

Each scenario uses a unique `--electronUserData` directory, Kogg state root, Theia
config root, and workspace. Close via the application API, wait a bounded period,
then force-kill only the harness-owned top-level app if graceful shutdown fails.
The product operation registry and OS observations decide whether product children
are residual; absence of the top-level Electron process alone is insufficient.

### Theia and its Playwright template

Theia's production workbench is highly asynchronous and contributions can appear
after the shell reaches ready. Stable page objects should wrap visible Explorer,
SCM, terminal, task, debug, command palette, notifications, editor, trust, and Kogg
widgets. Page objects centralize Theia-specific locators, but scenario prose and
assertions stay phrased as user actions/outcomes.

The command palette is a visible user boundary. Retrying palette discovery after
an extension activation delay is valid; directly calling `CommandRegistry` is
not. Likewise, opening a file through Quick Open is valid, while calling the file
service to simulate that action is not.

Workspace trust is part of the scenario, not setup to bypass. A trusted positive
scenario clicks the rendered trust choice. A refusal scenario leaves a repository
untrusted and verifies execution controls remain restricted.

### VS Code smoke tests

VS Code separates the launch/application driver from feature-area helpers and
runs smoke flows across desktop/web variants. That organization prevents one
monolithic script from hiding readiness, cleanup, or artifact behavior. Kogg
should create scenario fixtures plus page objects rather than continue expanding
one browser and one Electron script indefinitely.

VS Code automation sometimes uses product-specific driver hooks unavailable to a
person. Kogg rejects such hooks for causing feature behavior. Driver hooks may
collect window geometry, screenshots, process metadata, or logs after an outcome,
provided they remain observation-only and sanitized.

### Hosted runner images

The current matrix is Ubuntu 24.04, macOS 15, and Windows 2025. Kogg pins Node,
Python, Yarn, Theia, Playwright, Electron, and packaged artifacts, but OS patches,
window managers, shells, Git, compilers, and preinstalled tools can move. A run
manifest must record safe version/architecture/image facts and feature
qualification without copying environment variables, usernames, paths, or runner
tokens.

Linux is the mandatory governed-execution environment because Ranex confinement
qualification is Linux-specific. macOS and Windows must still prove browser,
native Electron, packaging, project/Git/UI, diagnostics, source maps, and safe
refusal of unqualified governed execution. Platform skips are explicit capability
results, never silent test omission.

### Ranex

Ranex real E2E reconstructs disposable repositories, invokes public process
boundaries, independently examines Git and journals, and includes discriminating
negative controls. This prevents tests that merely repeat the implementation's
claim. Kogg must preserve that independence: UI says what the user saw; Ranex
evidence/verdict and external Git/process inspection prove what occurred.

The Kogg harness does not parse private Ranex implementation state. It invokes the
production Kogg/Ranex path and uses stable public verification/evidence commands or
artifacts. It also proves no harness fixture can satisfy the acceptance check
without the real generated change.

## Current Kogg harness inventory and gaps

The repository already has useful real-boundary coverage:

- `scripts/e2e-browser.mjs` launches a real local signed registry and Kogg browser
  backend, authenticates through the visible login page, drives Chromium, exercises
  trust, diagnostics, marketplace, provider, editor/search, terminal/task, SCM,
  debug, projects, reload, and restart behavior, and inspects real files/Git;
- `scripts/e2e-electron.mjs` launches the real Electron main entrypoint with a
  clean profile, drives its native window, exercises marketplace/provider/editor,
  SCM/debug/projects/switching, captures failure evidence, and joins registry/app;
- packaging and smoke scripts classify and launch real artifacts; and
- CI runs unit/audit, browser E2E, native Electron E2E, packaging, and packaged
  smoke across Ubuntu, macOS, and Windows.

These scripts are a foundation, not yet the generated-feature harness. Principal
gaps are:

- they exercise pre-authored foundation fixtures, not a change generated by the
  real governed task loop from frozen specification through verdict/merge;
- browser/Electron files are monolithic and repeat page/action/cleanup logic;
- test orchestration children are tracked only by local variables, not a shared
  harness process registry and manifest;
- artifact policy is ad hoc and failure logs can be content-bearing;
- Windows browser conditions skip terminal/debug rendering while native coverage
  is separate rather than expressed as a capability matrix;
- retry/readiness behavior is local to individual commands rather than a named,
  bounded readiness contract; and
- the suite cannot yet correlate project/task/run/attempt/session/operation/
  worktree IDs from UI through logs, diagnostics, process cleanup, Ranex evidence,
  and artifacts.

## Required lifecycle, logging, and correlation

Use `[kogg:e2e:harness]` and `[kogg:e2e:artifact]` for test orchestration, and the
production logger names specified by each feature. Harness stable events are:

```text
run.requested|started|completed|failed
fixture.registered|started|ready|failed|cleanup.started|cleanup.completed|cleanup.failed
application.started|ready|failed|close.started|close.completed|close.timed-out
scenario.started|step.completed|completed|failed
artifact.capture.started|completed|refused|failed
residual-check.started|completed|failed
```

Permitted fields are scenario ID, platform/runtime enum, opaque correlation IDs,
fixture/application kind, step ID, safe code, counts, duration bucket, exit class,
and artifact kind/digest. Never log path, command/args, environment, prompt, source,
diff, terminal output, credential/cookie/header, provider body, remote URL, raw
exception body, or personal data.

The generated-feature scenario carries safe project, task, run, attempt, session,
operation, and worktree IDs. The harness obtains them only from visible safe UI or
redacted public artifacts; it does not query internal databases. Every ID must
join the expected logs, operation summary, diagnostic result, and Ranex evidence
without exposing the generated content.

## Failure, recovery, and oracle matrix

| Case | Visible product behavior | Independent proof |
| --- | --- | --- |
| Success | Generated feature is discoverable and works through its production control | Git/worktree commit/digest, build/package result, Ranex evidence/verdict, safe lifecycle, no residuals |
| Specification refusal | UI explains frozen-spec/policy refusal; no execution starts | No product child/worktree mutation; refusal evidence and clean diagnostics |
| Untrusted repository | Execution controls restricted | No task/provider/Ranex child; trust UI remains visible |
| Provider failure/refusal | Safe error with retry/decision state | Provider fixture observation or real provider safe outcome; no raw body/log leak |
| Spawn/readiness failure | Visible failed operation and diagnostic | Registered logical process, safe failure, cleanup, OS absence |
| Idle/absolute timeout | Stalled/timeout state and cancellation | Exact timeout trace, process-group/confinement cleanup, zero survivors |
| User cancel | Cancelling then cancelled; controls settle | No later mutation/evidence, idempotent cleanup and absence |
| Browser disconnect/reload | Reconnect restores authoritative operation state | Same operation ID, no duplicate request/mutation |
| App crash/restart | Recovery UI blocks new governed work until reconciled | Empty-queue startup sweep, recovery trace, durable evidence, child absence |
| Generated code fails build/test | User sees failed check and evidence; feature is not accepted/merged | Real compiler/test exit, unchanged protected branch, Ranex verdict |
| False positive calibration | Deliberately broken generated fixture must fail acceptance | Oracle distinguishes missing behavior even if UI loads |
| Cleanup/artifact failure | Run fails release gate, not merely warns | Residual/unsafe artifact check fails with safe code |

Retries repeat only discovery/action readiness that a user could repeat safely.
They never retry non-idempotent product actions such as submit, commit, merge,
install, or cancel without a product idempotency key. Each retry has a named
reason, attempt cap, and absolute deadline.

## Artifact and diagnostic contract

Each matrix job writes a run manifest, redacted lifecycle log, diagnostic report,
test result, and residual-process result. On failure it may add one screenshot per
runtime/window, a bounded sanitized console excerpt, and a Playwright trace only
if the scenario uses deterministic non-sensitive content and the trace passes the
artifact scanner. Video and network bodies are disabled by default.

Artifacts use random run IDs and digests, never repository/worktree paths. Store
them under `test-results/<run-id>/<platform>/<runtime>` locally and upload with a
bounded retention policy in CI. The scanner rejects credentials, cookies,
authorization, environment assignments, home/workspace paths, prompts, source,
diffs, terminal output, provider bodies, and known disposable canaries. A scanner
failure deletes/refuses upload and fails the run while preserving only a safe
scanner result.

The harness requires production diagnostics for every capability it exercises and
adds test-only checks for `e2e.fixtures`, `e2e.artifacts`, and `e2e.processes` to
the run manifest, not the product diagnostic catalog. Product diagnostics are
invoked through **Kogg: Run Diagnostics** and exported through the visible support
command.

## Real generated-feature scenario requirements

The production E2E in #70 must, through visible controls:

1. Create/select a project backed by a new disposable real Git repository.
2. Enter and freeze a small deterministic feature specification whose observable
   result cannot exist in the base commit.
3. Start the governed Kogg workflow with real configured role adapters; observe
   task/run/attempt state and cancellation controls.
4. Exercise real provider/Ranex/Git/worktree/check/build/test boundaries on the
   qualified Linux job and obtain bound evidence/verdict.
5. Accept or controlled-merge only after the required verdict; prove the protected
   branch and generated artifact correspond to that evidence.
6. Build/launch the resulting production browser and Electron surface and exercise
   the generated feature using its visible role/label/menu/command.
7. Restart with a clean window/profile against the durable project state and prove
   the feature and task evidence restore correctly.
8. Run diagnostics, export a support artifact, pause required debuggers, and prove
   source maps plus zero hidden/residual processes.
9. Repeat the principal refusal/failure, timeout, cancel, and crash/recovery
   controls with real boundaries and discriminating negative fixtures.
10. Run the portable UI/package subset on macOS and Windows and prove explicit
    safe refusal for unqualified governed Linux-only execution.

The feature fixture is specified by observable outcome and public inputs, not a
pre-generated patch. The harness may seed the base repository and specification,
but the production agents must create the change during the run. A committed
fixture containing the expected successor code invalidates the test.

## Rejected approaches

- Directly calling Kogg JSON-RPC/services or command registry to cause behavior.
  This bypasses the human and frontend boundary.
- Mocking Git, filesystem, provider CLI, subprocess, Ranex, confinement, build,
  test, or package boundaries owned by the scenario.
- Pre-generating or checking in the accepted patch, successor commit, or compiled
  feature artifact.
- Treating a page load, shell-ready state, screenshot, or success toast as proof
  of external state or cleanup.
- Using arbitrary sleeps as readiness. Use visible state, protocol readiness, or
  bounded polling of an independent oracle.
- Retrying submit/commit/merge/install actions to hide missing idempotency.
- Calling Electron main evaluation or OS APIs to invoke feature behavior. These
  are observation/cleanup fallbacks only.
- Reusing a developer profile, credentials, repository, global Git config, keychain
  entry, state database, or installed extension.
- Uploading raw Playwright traces, videos, HAR/network bodies, console logs,
  screenshots, environments, or temporary paths without deterministic content and
  scanner approval.
- Declaring unsupported platform behavior skipped without a visible safe refusal
  and capability record.
- Letting one monolithic script own every page, fixture, process, oracle, artifact,
  and scenario responsibility.

## Prototype recommendation

The highest-risk assumption for #65 is that the harness can kill and restart the
real native Electron/Kogg application while a real Kogg-owned child and governed
operation are active, then distinguish harness children from product/Ranex
children, recover through visible UI, preserve evidence, and prove no residual
process without using internal services or leaking content.

The disposable prototype must:

- launch the pinned Electron app, local deterministic provider, real Git repo,
  bundled Python/Ranex bridge, and one bounded child through production UI;
- record register/start/activity before killing the top-level app at a controlled
  point, with an otherwise empty new-work queue;
- relaunch from the normal entrypoint and drive visible recovery/diagnostics;
- prove same-operation correlation, idempotent reconciliation, evidence integrity,
  and product/harness/Ranex ownership separation;
- run an unrelated PID-reuse/identity calibration and prove it is never signalled;
- capture only scanner-approved redacted artifacts;
- prove source-level debugger access in every affected runtime; and
- report explicit Ubuntu/macOS/Windows capability findings without inventing a
  portable PID-only cleanup fallback.

If Playwright Electron cannot reliably drive the pinned packaged/native boundary,
the prototype must reopen #62 and select an explicitly licensed driver. It must
not fall back to browser-only automation or main-process command invocation.

## Decision-complete production pseudocode

This section is normative for #65 and #70. The prototype may disprove a choice
with real evidence; it may not silently choose a different driver, authority,
state, retry, artifact, or cleanup policy.

### Repository topology and authority

Keep the harness outside production bundles:

```text
tests/e2e/generated-feature/
  contract.ts                 closed scenario, manifest, event, result DTOs
  harness-process-manager.ts  test-only register-before-spawn owner
  run-controller.ts           deadline, phase, cleanup, final verdict
  artifact-manager.ts         closed capture policy, scanner, retention result
  capability.ts               matrix qualification and refusal assertions
  fixtures/                   Git, registry/provider, profile, specification
  drivers/browser.ts          browser production launch adapter
  drivers/electron.ts         native production launch adapter
  pages/                      visible workbench/Kogg area objects
  oracles/                    public Git, filesystem, process, Ranex verifiers
  scenarios/                  success and principal terminal paths
scripts/e2e-generated-feature.mjs
```

The run controller is the sole harness lifecycle writer. The harness process
manager owns only runner-created top-level processes and fixtures. Playwright
owns Chromium/Electron launches. Kogg, Theia, providers, and Ranex retain their
production ownership described by #64. Oracles are read-only and cannot cause a
product transition. Page objects cause behavior only through rendered controls.

### Closed contracts

```ts
type Runtime = 'browser' | 'electron';
type Platform = 'linux' | 'macos' | 'windows';
type RunState =
  | 'requested' | 'starting' | 'active' | 'cleaning'
  | 'completed' | 'failed' | 'timed-out' | 'cancelled';
type FixtureState =
  | 'registered' | 'starting' | 'ready' | 'failed'
  | 'cleaning' | 'cleaned' | 'cleanup-failed';
type StepState = 'pending' | 'active' | 'passed' | 'failed' | 'timed-out';
type ArtifactDecision = 'retained' | 'refused' | 'deleted' | 'not-requested';
type SafeCode =
  | 'E2E_FIXTURE_START_FAILED' | 'E2E_APPLICATION_NOT_READY'
  | 'E2E_VISIBLE_CONTROL_MISSING' | 'E2E_STEP_FAILED'
  | 'E2E_IDLE_TIMEOUT' | 'E2E_ABSOLUTE_TIMEOUT'
  | 'E2E_CLEANUP_FAILED' | 'E2E_RESIDUAL_PROCESS'
  | 'E2E_ARTIFACT_UNSAFE' | 'E2E_ORACLE_MISMATCH'
  | 'E2E_CAPABILITY_UNQUALIFIED';

interface Correlations {
  runId: string; scenarioId: string; projectId?: string; taskId?: string;
  attemptId?: string; sessionId?: string; operationId?: string;
  worktreeId?: string;
}
interface ScenarioDefinition {
  schemaVersion: 1; id: string; runtime: Runtime;
  requiredCapabilities: readonly Capability[];
  totalTimeoutMs: number; steps: readonly StepDefinition[];
  expectedTerminal: RunState; expectedProductTrace: readonly TraceMatcher[];
  expectedHarnessTrace: readonly TraceMatcher[];
}
interface RunManifest {
  schemaVersion: 1; correlations: Correlations; platform: Platform;
  runtime: Runtime; state: RunState; safeCode?: SafeCode;
  capabilities: readonly CapabilityResult[]; fixtures: readonly FixtureSummary[];
  steps: readonly StepSummary[]; artifacts: readonly ArtifactSummary[];
  productDiagnostics: readonly DiagnosticSummary[];
  harnessChecks: readonly HarnessCheck[]; residualCount: number;
  environment: SafeEnvironmentFacts;
}
```

All objects reject unknown fields. IDs are random UUID v4 values. Durations are
bucketed in shared logs and exact only in local test results. Environment facts
are closed enums and tool versions; no path, username, hostname, environment
map, remote URL, or runner label is admitted.

### Harness state and persistence

Write one manifest atomically after every transition using temporary-file plus
rename within the run artifact directory. The previous valid manifest remains
readable after interruption. Transitions are:

```text
run: requested -> starting -> active -> cleaning -> completed
                                |          |------> failed
                                |          |------> timed-out
                                |          `------> cancelled
                                `-----------------> cleaning
fixture: registered -> starting -> ready -> cleaning -> cleaned
                         |          |          `-> cleanup-failed
                         `-> failed -> cleaning
step: pending -> active -> passed|failed|timed-out
```

Every run reaches `cleaning` exactly once. A scenario result is successful only
when its expected product result, independent oracles, product diagnostics,
harness checks, artifact decision, and zero-residual assertion all pass. Cleanup
or artifact refusal overrides an otherwise successful product outcome to
`failed`. Conflicting terminal writes fail the run.

### Register-before-spawn and cleanup algorithm

For every harness fixture or top-level application:

```text
allocate opaque fixture ID
append fixture.registered and persist manifest
construct fixed launch configuration in memory
append fixture.started immediately before spawn
spawn in owned process group where supported
bind PID privately; never persist or log it
wait for named readiness oracle within fixture deadline
append fixture.ready or fixture.failed(safe code, error type)
on any terminal path, enter run.cleaning
close Playwright contexts/windows, then application, then fixtures in reverse order
wait for exit and stream close separately
after grace deadline, force only the harness-owned top-level/process group
ask product diagnostics and responsible owner about product descendants
independently assert all harness PIDs/fingerprints absent
append cleanup result; delete disposable state only after observation completes
```

PID-only signalling after restart is forbidden. The process manager stores a
private platform creation fingerprint and signals only a matching owned process.
An unverifiable identity yields `E2E_RESIDUAL_PROCESS`, preserves safe evidence,
and fails closed. Product descendants are never killed by harness name scanning.

### Production launch adapters

`BrowserDriver.launch` starts the real browser backend with isolated Kogg/Theia
state, then asks Playwright for a fresh Chromium context and drives the rendered
authentication and workbench. `ElectronDriver.launch` uses Playwright Electron
against the production main entrypoint with a unique user-data directory. Both
return the same interface:

```ts
interface ProductionDriver {
  waitForWorkbench(deadline: Deadline): Promise<WorkbenchPages>;
  visibleCorrelations(): Promise<Correlations>;
  screenshot(kind: 'failure'): Promise<CandidateArtifact>;
  closeGracefully(deadline: Deadline): Promise<CloseResult>;
  observeTopLevel(): Promise<'running'|'exited'|'unverified'>;
}
```

Electron main-process evaluation is limited to launch facts, window enumeration,
and observation required for cleanup. It cannot invoke commands, services, menu
handlers, or feature code. Browser page evaluation is limited to accessibility
and rendered-state observation that Playwright cannot expose directly; it cannot
cause product behavior or read internal services.

### Page-object and visible-action contract

Page objects expose semantic actions for Authentication, Trust, Projects, Task,
Workflow, Operations, Evidence, Diagnostics, SCM, Editor, Terminal, Debug, and
GeneratedFeature. Each action locates by role, accessible name, label, rendered
text, command palette, or visible menu. An app-owned test ID is permitted only
for disambiguating repeated rendered rows and must identify no hidden control.

`discover` actions may retry while a visible asynchronous contribution becomes
available. `submit`, `freeze`, `start`, `cancel`, `accept`, `merge`, `install`,
and `delete` execute once with an idempotency request established by product UI.
After a click, web-first assertions wait for the next visible authoritative
state. Arbitrary sleep and internal command/service calls are prohibited.

### Deadlines and retry policy

The run has a 30-minute absolute deadline on qualified Linux and 15 minutes for
portable refusal/smoke scenarios. Fixture readiness is 60 seconds, workbench
readiness 120 seconds, visible contribution discovery 30 seconds, ordinary UI
steps 15 seconds, graceful application close 15 seconds, and final cleanup 30
seconds. CI may multiply these constants once by the repository slow-runner
factor; individual scenarios cannot invent timeouts.

Discovery retry uses at most five attempts with 100, 250, 500, 1000, and 2000 ms
delays, bounded by the step deadline. It records only attempt count and safe
reason. A deadline aborts pending waits, enters cleanup, and emits exactly one
idle or absolute timeout result. No timeout may leave cleanup unbounded.

### Artifact manager and scanner

Capture is deny-by-default. Passing runs retain only manifest, redacted lifecycle
events, test result, diagnostic summary, residual result, and public Ranex
evidence digest/verdict. Failure may request one screenshot per window, one
bounded sanitized console excerpt, and one Playwright trace. Video, HAR, request/
response bodies, terminal output, and raw process output are disabled.

Before retention, the scanner recursively inspects filenames, text, structured
values, archive members, image OCR output where available, and known canaries.
It rejects credentials/tokens/cookies/authorization, environment assignments,
home/workspace paths, usernames, prompts, source, diffs, terminal/provider bodies,
Git remotes, and personal data. Rejected candidates are moved to a private
disposal area, deleted before upload, and represented only by artifact kind and
`E2E_ARTIFACT_UNSAFE`. Scanner errors are refusals, not passes.

### Logging, diagnostics, and source maps

Use the research logger prefixes and event names exactly. Every event carries
only correlations plus the closed field allowlist. Failures include a safe code
and error type, never an exception message or body. Lifecycle order is asserted
from the redacted event stream.

Product diagnostics are invoked through visible controls and must include all
feature-owned catalog checks plus #64 operation registry, recovery, processes,
cleanup, and admission checks. Harness-only manifest checks are:

```text
e2e.fixtures   all registered fixtures reached terminal cleanup
e2e.processes  all privately bound harness identities are absent
e2e.artifacts  every retained artifact passed the closed scanner
e2e.oracle     UI, Git/filesystem, Ranex evidence, and product state agree
e2e.source-map required runtime pauses map to repository source statements
```

The harness attaches the browser, backend Node inspector, Electron main/renderer,
affected plugin/debug adapter, and Linux Python adapter at explicit breakpoint
markers reached by the visible workflow. It records runtime and mapped source
line only. A generated bundle frame without an original repository source fails.

### Capability decisions

Linux is the only V1 platform allowed to run the governed generation scenario.
It must report qualified Ranex confinement before start. macOS and Windows run
the full portable browser/Electron/project/Git/diagnostic/package surface and
must visibly refuse the governed start with `E2E_CAPABILITY_UNQUALIFIED` and no
provider/Ranex/worktree child. Windows terminal/debug coverage is required in
native Electron; inability is a release blocker, not a skip.

Capabilities are probed and recorded before scenario selection. A required
capability that is absent runs its specified visible refusal scenario. No test
framework skip can satisfy a product refusal or release requirement.

### Exact expected traces

```text
harness success:
  run.requested -> run.started -> fixture.registered* -> fixture.started* ->
  fixture.ready* -> application.started -> application.ready ->
  scenario.started -> step.completed* -> scenario.completed ->
  artifact.capture.started -> artifact.capture.completed ->
  residual-check.started -> residual-check.completed ->
  application.close.started -> application.close.completed ->
  fixture.cleanup.started* -> fixture.cleanup.completed* -> run.completed

fixture failure:
  run.requested -> run.started -> fixture.registered -> fixture.started ->
  fixture.failed(E2E_FIXTURE_START_FAILED) -> fixture.cleanup.started ->
  fixture.cleanup.completed -> residual-check.completed -> run.failed

product timeout/cancel:
  ... scenario.started -> step.completed(start) -> operation.stalled ->
  operation.timeout -> cleanup.started -> process.exit -> cleanup.completed ->
  step.completed(timeout-visible) -> scenario.completed -> harness cleanup

application close timeout:
  ... application.close.started -> application.close.timed-out ->
  fixture.cleanup.started -> fixture.cleanup.completed ->
  residual-check.completed -> run.failed(E2E_CLEANUP_FAILED)

unsafe artifact:
  ... artifact.capture.started -> artifact.capture.refused ->
  residual-check.completed -> cleanup -> run.failed(E2E_ARTIFACT_UNSAFE)

unqualified platform:
  ... application.ready -> scenario.started -> step.completed(refusal-visible) ->
  residual-check.completed(productChildCount=0) -> cleanup -> run.completed
```

Product success/refusal/failure/timeout/cancel/restart traces are those fixed by
the owning feature packets and #64. The harness must match them by safe IDs and
order; it cannot substitute its own events for missing product evidence.

### Required scenario set and production gate

Implement separate scenarios for generated-feature success, false-positive
calibration, frozen-spec refusal, untrusted repository, provider refusal, spawn/
readiness failure, build/test failure, idle and absolute timeout, user cancel,
browser reload, application crash/restart recovery, cleanup failure, unsafe
artifact refusal, and macOS/Windows unqualified execution. Each starts with a
clean profile and disposable repository and ends with the common cleanup oracle.

The success scenario freezes observable inputs, lets real configured agents
create the successor, obtains real Ranex evidence/verdict, performs controlled
merge, builds/launches the production surface, and uses the generated visible
control. The negative calibration removes or breaks the successor behavior and
must fail the same oracle even though the workbench loads.

scanner rule, and cleanup override; integration tests with real processes and
atomic manifests; browser and native Electron scenarios on all three platforms;
qualified governed scenarios on Ubuntu; packaging and packaged smoke; artifact

diagnostic, artifact decision, or lifecycle join blocks release.
